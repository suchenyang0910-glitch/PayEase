# PayEase V1 技术选型与工程约束

## 1. 选型原则

- 三域独立：`broker-platform`、`lender-core`、`employer-portal` 独立部署、数据库、密钥与身份边界。
- 先单体模块化、后按边界拆分；V1 不引入无业务收益的微服务、链上组件或多云。
- 所有关键依赖采用 LTS、锁文件、最小权限和可替换接口。

## 2. 推荐 V1 栈

| 层          | 推荐                                                          | 约束                                                            |
| ----------- | ------------------------------------------------------------- | --------------------------------------------------------------- |
| 语言/运行时 | TypeScript、Node.js 22 LTS、pnpm 9 固定版本                   | CI 与本地必须使用项目锁定版本                                   |
| Web 前端    | React + Vite + React Router                                   | Mini App 与后台按不同 CSP/XFO 策略发布                          |
| 后端        | NestJS 或 Fastify 模块化服务                                  | 以 REST/OpenAPI 3.1 为跨域边界；禁止跨库读写                    |
| 数据库      | PostgreSQL 16                                                 | 每域独立集群；RLS 只用于租户内二次防线，不替代网络隔离          |
| 数据访问    | Drizzle ORM + SQL migration                                   | 参数化查询；迁移与审计触发器纳入版本控制                        |
| 缓存/幂等   | Redis                                                         | 仅作会话、限流、nonce、幂等与短期队列状态；不可作为账务事实来源 |
| 异步任务    | SQS + DLQ（S0.2 后）                                          | 回调、通知、文件扫描、重试均可追踪且可重放                      |
| 文件        | S3 + SSE-KMS + 对象锁                                         | 服务端信封加密、病毒扫描、重编码；禁止公共桶                    |
| 部署        | AWS ECS Fargate + ALB + WAF                                   | 三域独立账号/VPC；不在 S0.2 前创建                              |
| 可观测性    | OpenTelemetry、CloudWatch、CloudTrail、GuardDuty/Security Hub | 日志结构化与脱敏；审计事件单独存储                              |
| 测试        | Vitest、Playwright、Hurl、Schemathesis、ZAP                   | 先 fixture，再沙箱，最后受控生产演练                            |

## 3. 必须明确的技术决策

| ADR    | 决策                                         | 截止点        |
| ------ | -------------------------------------------- | ------------- |
| ADR-01 | 主区域、DR 策略与跨境数据法律意见            | S0.2 签字     |
| ADR-02 | 后端框架（NestJS 或 Fastify）与迁移工具      | S0.2 结束前   |
| ADR-03 | Telegram Bot、会话 cookie 域与 Mini App 域名 | S1 开始前     |
| ADR-04 | 首家机构的 OpenAPI、mTLS/签名算法与回调 SLA  | S4 开始前     |
| ADR-05 | 文件扫描方案与文档保留/删除策略              | S1 文件能力前 |
| ADR-06 | 还款通道与对账事实来源                       | S5 开始前     |

## 4. 非功能性验收下限

- API：敏感写操作幂等；跨域回调签名、时间窗、nonce 与重试/DLQ 全覆盖。
- 数据：金额不使用浮点；T0/T1 加密与最小披露；审计事件不可更新或删除。
- 权限：每个 API 有 200/401/403、同租户/跨租户和红牌字段测试。
- 可靠性：备份恢复、消息重放、回调乱序、对账差异、密钥泄露至少各演练一次。
- 性能：以首个试点预估峰值的 3 倍执行压测并设定容量报警阈值。

## 5. 当前禁止的技术项

- S0.2 前：Terraform、AWS SDK/真实云资源、真实身份或第三方 SDK。
- V1：自营资金池、自动授信决策、企业代扣、多机构智能路由、Web3 结算。
- 永久：共享业务数据库/共享域密钥、CVV 存储、明文证件/账户/薪资日志。
