## 2. 状态机设计原则

### 2.1 权威域原则

1. 持牌机构域负责授信结果、最终合同、放款、托管钱包到账、提现、银行/支付机构授权还款核销、结清等信贷核心权威状态。
2. KhmerX 助贷域负责申请采集、资料预审、企业核验、用户交互、证据采集、费用凭证采集与回传。
3. Broker 域中的部分状态是对持牌域事件的本地投影，例如 `LENDER_DECISION_RECEIVED`；该名称本身不应被视为持牌域权威状态。
4. 任何跨域状态变化都必须由事件驱动，不允许本地域直接伪造对方域的权威结论。
5. `broker_db` 只保存 `brokerApplicationRef` 的本地状态与持牌回调投影；`lender_db` 只保存 `lenderCaseRef` 的本地状态与助贷事件投影。
6. 跨域只通过 append-only event envelope 同步；不存在由两个域共同写入的 `application.status`。

### 2.2 投影与可见性原则

1. 用户端与普通助贷运营端只看受控投影文案，不直接暴露持牌机构内部状态名。
2. 每个状态必须明确：
   - 权威域
   - Broker 投影名
   - 用户可见文案
   - 可操作角色
   - 进入事件
   - 退出事件
   - 非法迁移处理

### 2.3 非法迁移原则

所有未定义迁移一律：

- 返回 `409 INVALID_STATE_TRANSITION`
- 写入 append-only 审计事件
- 记录 `eventId`、来源域、操作者/系统、前状态、目标状态、原因码、`workflowVersion`

## 4. 关键状态修正规则

### 4.1 `LENDER_DECISION_RECEIVED`

1. `LENDER_DECISION_RECEIVED` 是 Broker 收到持牌结果后的本地投影状态。
2. 持牌域不以该名称作为其权威状态名；持牌域对应事实事件为 `DECISION_MADE` / `DECISION_AVAILABLE`。
3. 只有当 Broker 成功接收并验签回调后，才能进入 `LENDER_DECISION_RECEIVED`。

### 4.2 合同确认链路

正确链路如下：

```text
Lender: FINAL_CONTRACT_READY
Broker: CONTRACT_EVIDENCE_COLLECTED
Broker -> Lender: CONTRACT_EVIDENCE_SUBMITTED
Lender: CONTRACT_EVIDENCE_ACCEPTED
Lender: READY_FOR_DISBURSEMENT
```

规则：

1. KhmerX Mini App 负责展示不可篡改合同快照、采集签名/视频与还款授权说明确认。
2. 持牌机构必须验收合同证据后，才能进入放款准备与放款阶段；融资居间服务费不再作为放款前置条件。
3. 不能使用单一 Broker 状态替代持牌机构的合同证据验收事实。

### 4.3 放款后费用与还款链路

1. 放款成功是居间服务费应收产生的唯一条件，费用验收不得阻塞 `READY_FOR_DISBURSEMENT` 或 `DISBURSED`。
2. Broker 在收到已验签 `DISBURSED` 后，按“工厂有效费率优先、平台默认费率兜底”冻结 `BROKERAGE_REMUNERATION_DUE`；在 D+1、D+2、D+3 提醒，D+3 未验收进入 `BROKERAGE_REMUNERATION_OVERDUE`。
3. 借款利息不在放款前支付。持牌机构按冻结的一/两期账单收取“本期本金 + 本期利息”；用户到期或提前还款时，必须主动跳转本人银行或支付机构完成授权。
4. 两期计划中，本金与总利息分别对半分配，最小货币单位余数进入第二期；发薪节点只用于还款日提示与能力评估，不得生成工资代扣执行状态。
5. Broker 的居间服务费事实与 Lender 的钱包、提现、本息回款事实各自独立记录、独立验收，不再定义 `PRE_DISBURSEMENT_PAYMENTS_*` 聚合状态。

### 4.4 补件恢复链路

1. `BROKER_SUPPLEMENT_RESUBMITTED` 不能直接让持牌域退出“补件中”。
2. Broker 补件后，只能发送跨域事件；持牌域接收并验收后，才能进入：
   - `LENDER_SUPPLEMENT_RECEIVED`
   - `LENDER_REVIEW_RESUMED`
3. 持牌域是否恢复审核，必须由持牌域自己写入权威状态。

### 4.5 钱包、提现与主动还款链路

钱包、提现和还款不能再沿用工资扣款状态链路。正确链路：

```text
DISBURSED
-> WALLET_CREDIT_PENDING
-> WALLET_AVAILABLE
-> WITHDRAWAL_PROCESSING / REPAYMENT_DUE
-> REPAYMENT_INTENT_CREATED
-> REPAYMENT_AUTHORIZING
-> REPAYMENT_PROCESSING
-> PAID_OFF / REPAYMENT_EXCEPTION
```

规则：

1. 放款后必须先经持牌机构或支付通道验签确认，才能进入 `WALLET_AVAILABLE`。
2. 用户提现只作用于持牌机构托管钱包余额；失败、取消、超时或回滚不得错误扣减可用余额。
3. 还款成功只能由银行或支付机构的已验签回调，加上持牌机构核销事实驱动进入 `PAID_OFF`。
4. 回调金额不一致、授权取消、通道超时、对账失败都必须进入 `REPAYMENT_EXCEPTION`，不得自动结清。
5. 每个 `REPAYMENT_INTENT_CREATED` 必须引用不可变的 `repaymentPlanSnapshot`、`repaymentAuthorizationSnapshot`、`walletPolicyVersion` 与外部通道订单引用；已签约订单不得因后续规则更新而重排。

### 4.6 `REJECTED`

1. `REJECTED` 必须为终态。
2. 满足重新申请条件时，必须创建新的 `applicationNo`。
3. 新申请应引用旧申请作为来源关系，但不得把旧订单重新改回 `SUBMITTED`。

### 4.7 关闭链路

1. `CLOSED` 不再作为共享状态名使用。
2. 必须拆成各域本地状态/事件：
   - `BROKER_CLOSED` / `BROKER_CASE_CLOSED`
   - `LENDER_CLOSED` / `LENDER_CASE_CLOSED`
3. 用户端只显示统一投影文案“已关闭”。
4. 各域保留自己的关闭记录和投影，不能共用一个双权威状态事实。

## 5. 角色边界补充

### 5.1 企业 HR / 企业管理员

负责：

- 在职状态
- 工资确认值或工资区间
- 工龄
- 劳动合同状态

不得负责：

- 钱包、提现或还款执行结果核销
- 融资居间服务费验收（该费用为放款后独立应收）
- 持牌机构审批

### 5.2 企业财务（`EMPLOYER_FINANCE`）

V1 不承接贷款本息扣款、还款授权、钱包处理或核销职责；该角色在当前基线中不参与贷款主流程实现。

不再参与：

- 在职核验
- 工资核验审批
- 工龄/合同状态核验
- 贷款本息扣款执行或回填
- 钱包、提现、还款异常处理

## 6. 三类付款凭证模型

三类付款凭证必须完整建模：

1. `BROKERAGE_REMUNERATION_PAYMENT_PROOF`
   - 收款主体：KhmerX
   - 权威验收方：Broker

2. `LENDER_INTEREST_PAYMENT_PROOF`
   - 收款主体：持牌机构
   - 权威验收方：Lender

3. `EXCEPTIONAL_REPAYMENT_PAYMENT_PROOF`
   - 用途：银行/支付机构授权失败、回调异常或线下补款时的异常还款补证
   - 权威验收方：Lender

推荐实现：

```text
payment_proof
  + payment_allocations[]
```

其中每条 allocation 至少包含：

- `payeeDomain`
- `paymentType`
- `amountMinor`
- `currency`
- `reviewStatus`
- `acceptedByDomain`

## 7. 历史订单切换策略

### 7.1 已结清 / 已关闭历史订单

1. 保留原 `workflowVersion`。
2. 只读展示，不重算、不回写新状态。
3. 历史 `netDisbursement`、旧期限、旧凭证类型仅作为快照保留，用于审计和历史可读性。

### 7.2 进行中旧订单

必须新增以下切换记录：

- `legacyStatus`
- `workflowVersion`
- `cutoverDecision`
- `cutoverAt`
- `cutoverOperator`

人工决策仅允许：

- `CONTINUE_LEGACY_FLOW`
- `CUTOVER_TO_V2`

未作人工决策前，不自动切换。

### 7.3 新建订单

1. 仅允许 `workflowVersion = V2`。
2. 仅允许一次还款（下一合格发薪节点）或两次还款（连续两个合格发薪节点）；节点版本与还款计划必须冻结。
3. 用户端停止以 `netDisbursement` 作为主展示字段。

### 7.4 历史字段与旧口径处理原则

#### `7-180 天`

- 停止新订单使用
- 保留历史快照与审计可读性

#### `netDisbursement`

- 停止新订单作为用户主展示字段
- 保留历史快照，不参与新口径重算

#### 旧付款凭证

- 不删除旧表
- 不删除历史审计
- V2 之后新记录必须写明三类之一或通过 `paymentAllocations` 拆分归属

#### `finance-verify-portal` 旧字段

- 仅在新页面与新 DTO 中停止展示申请金额、期限、利息、持牌机构名等字段
- 不删除已有历史数据与审计记录

## 8. 非法迁移与错误码规则

所有状态机实现必须满足：

1. 非法迁移返回 `409 INVALID_STATE_TRANSITION`
2. 越权操作返回 `403 FORBIDDEN__ROLE_OUT_OF_SCOPE`
3. 跨域越权返回稳定错误码并写审计
4. 所有状态迁移都必须记录：
   - `eventId`
   - `workflowVersion`
   - `sourceDomain`
   - `targetDomain`
   - `actorUserRef` 或系统标识
   - `fromStatus`
   - `toStatus`
   - `reasonCode`
   - `occurredAt`

## 9. M0-02 放行条件

仅当本文档与 M0-01 v2 其余结论一起通过审核后，才允许进入 M0-02，并且第一批实现仅允许：

1. 新状态机、事件、权威域/可见域/可操作角色模型；
2. `ProductRule`、`FeeRule`、`ContractVersion`、`EmployerPayrollRule`；
3. 三类付款凭证模型；
4. 费用/期限纯函数与 fixture；
5. 对应迁移、单元测试、兼容策略。

仍暂不允许：

1. 删除旧付款凭证路由；
2. 移动合同用户交互页面；
3. 修改生产数据；
4. 将现有 `broker-api` 中的持牌路由直接删除；
5. 提交、推送、部署。
