# Trae V1 两域薪资贷三天编码冲刺任务

**周期**：3 个连续工作日｜**目标**：完成符合新规范的 P0 垂直切片，并交由 Codex 审查。
**不是目标**：三天内完成真实银行代扣、真实持牌机构/征信/支付/活体接口、生产上线或全部 UI 精修。以上能力只做默认关闭的模型、Stub、权限和验收。

## 每日共同规则

1. 开工前读取 [规范基线](../00-导航与治理/V1_两域薪资贷_规范基线.md)、[产品与流程](../01-产品与业务/V1_两域薪资贷_需求与业务流程.md)、[技术规范](../03-架构与数据/V1_两域薪资贷_技术架构与数据规范.md)、[接口安全规范](../06-接口与集成/V1_两域薪资贷_接口与网络传输安全规范.md)。
2. 只在现有代码基础上重构业务域；保留认证、安全门禁、金额类型、审计基础和两域项目结构。
3. 每天结束前必须提交：改动文件清单、迁移影响、接口影响、测试命令与结果、未解决风险。**不得自行提交、推送或部署。**
4. 不得接真实外部 SDK/密钥/账户；不得录入真实 PII、合同、证件、视频或支付凭证。

## Day 1：规则快照与旧模型清理

### 目标

消除新订单路径中的旧口径，建立可测试的 15/30 天、发薪节点、三种回收方式和费用/分润版本模型。

### Trae 编码任务

1. 对现有未提交 M0-02 代码逐文件对照规范，列出并替换：
   - 放款前费用验收阻塞；
   - `7–180` 天新订单期限；
   - 企业仅扣本金；
   - 共同跨域状态或跨域直读假设。
2. 建立/调整纯领域模型：
   - `EmployerPayrollRuleVersion`：1–2 个发薪节点、允许回收方式、默认方式、有效期、法务启用标志；
   - `RepaymentMethodSnapshot`：三种方式之一、用户授权引用、收款主体引用、冻结时间；
   - `RepaymentPlanSnapshot`：15/30、一次/两次节点、本息分配、缓冲期、规则版本；
   - `BrokerageRemunerationRuleVersion` 与 `EmployerRevenueShareRuleVersion`。
3. 编写纯函数和 fixture：
   - 15/30 合法性；
   - 一次/连续两节点校验；
   - 两期本金/利息拆分与余数归第二期；
   - 工厂覆盖平台费率；
   - 三种回收方式的前置校验；
   - D+1/D+2/D+3、T-3/T-1/T、工资日后 3 天缓冲。
4. 所有新金额 DTO 使用 `amountMinor: string + currency`；补负向测试拦截 `number`。

### Day 1 验收

- 旧口径不再影响新订单路径；历史快照只读保留。
- 纯函数测试覆盖：奇数分币、月末、单节点、双节点、缺授权、未启用工资扣款/Direct Debit、重复计算。
- `pnpm format:check`、相关 `typecheck` 与定向测试通过。

## Day 2：企业权限、申请选择与授权证据

### 目标

让用户可在最终要约前选择合法可用的回收方式；让企业 HR/财务只能完成各自职责。

### Trae 编码任务

1. 数据迁移与权限：
   - 工厂资料：对接人、书面授权收款主体、发薪节点、允许回收方式、有效费率/分润规则引用；
   - HR 仅核验身份/在职/合同/工龄/授权工资事实；
   - 财务仅查看已授权的最小化工资扣款清单，回填已扣/部分扣/未扣及凭证引用；
   - 所有跨租户、跨角色、敏感字段读取/导出一律 403。
2. Mini App：
   - 最终要约页显示服务端生成的可选回收方式；不满足前置的方式不展示或明确不可选；
   - 选择企业工资扣款或本人账户代扣时展示独立授权；不得默认勾选；
   - 展示本金、利息、融资居间服务费、实际到账、还款节点、缓冲期和规则版本；
   - 采集签名与确认视频的**元数据/受控占位证据**，不接第三方电子签/活体服务。
3. 助贷运营端：服务费只在 `DISBURSED` 事件后建立应收和 D+1/D+2/D+3 提醒；保持经办/复核分离。

### Day 2 验收

- 工厂 A 的 HR/财务无法读取或写入工厂 B 资料。
- 财务清单不含完整证件、账户、联系人、费率、服务费、持牌合同或内部评分。
- 未授权的工资扣款/Direct Debit 选择被服务端拒绝；用户主动付款为可用兜底。
- 合同/授权/签名/视频证据均有关联版本、Hash、语言、时间和审计事件。
- Day 1 门禁继续通过，加上权限和 UI 定向测试。

## Day 3：两域事件、人工核销与受控 UAT

### 目标

跑通“申请→企业核验→机构结果→合同证据→放款→服务费→三种回收→核销”的 Stub 垂直切片。

### Trae 编码任务

1. 完成两域 Outbox/Inbox 和契约：
   - 申请包、要约/合同、合同证据、放款确认、工资扣款回填、银行代扣结果、用户付款核销、异常事件；
   - 事件含签名校验接口、时钟窗口、nonce、防重放、幂等、乱序与死信处理；真实 mTLS 证书只做配置接口，不写真实值。
2. 持牌域：
   - 放款经办/复核、回收/核销经办/复核；
   - 企业回填、银行回调、用户付款凭证均仅作为待核销事实，不能自动结清；
   - 部分扣、未扣、代扣失败和过期授权进入异常工单。
3. 工厂分润：
   - 仅实现工厂收款主体、固定月度/放款本金比例两种规则、结算资格纯函数、对账单 Stub；
   - HR/财务个人激励只显示“默认关闭”，不实现个人收款。
4. 添加 UAT fixture：三种回收方式各一条成功链路，另加跨租户、重复事件、乱序事件、部分扣、服务费未确认、退款冲回等失败链路。

### Day 3 验收

- Stub 端到端流程完整，两个域无共享数据库或内部 ID。
- 坏签名、过期时间、重复 nonce/event、乱序回调、非法状态、重复核销均被拒绝或安全处理。
- 放款成功前无服务费应收；服务费不进入任何本息回收指令。
- 只有持牌机构双人复核能将本息结清；分润不因重复事件重复生成。
- 全量格式、类型、单元、集成、金额、安全和权限门禁通过。

## 三天结束交接包

Trae 必须提交给 Codex：

1. 逐日变更摘要与尚未完成项；
2. 迁移顺序、回滚策略、受影响的数据表；
3. API 契约/fixture 变更清单；
4. 测试结果与失败项（如有）；
5. 不含任何真实敏感信息的 UAT 证据；
6. 需要产品/法务确认的阻塞项。

## Codex 审查结论标准

只有 Day 1–3 验收全部通过，且无越界功能、无真实敏感信息、无旧口径残留时，才进入提交审查；不通过则只修复失败项，禁止推送或部署。
